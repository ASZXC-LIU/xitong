# 分单系统 UI 详细规范

## 1. 设计目标

界面首先服务于“看得懂、点得准、不容易填错”。员工端用户可能不熟悉手机操作，页面应像清晰的工作单，而不是数据看板。管理员响应式 Web 需要在桌面高效承载大矩阵，并在手机浏览器把必要操作转化为适合触控的布局；两端角色界面都要稳定、克制和可追踪。

优先级从高到低：正确与防误操作、可读性、操作效率、响应式可用、视觉一致性、装饰效果。

## 2. 基础视觉令牌

在没有现有设计令牌可复用时采用以下基线；若项目已有近似变量，统一到变量而不是重复硬编码。

| 类别 | 基线 |
| --- | --- |
| 页面背景 | `#F5F7FA` |
| 卡片/表格背景 | `#FFFFFF` |
| 主文字 | `#1F2937` |
| 次文字 | `#667085`，仅用于辅助信息 |
| 边框 | `#D0D5DD` |
| 主操作 | `#1677FF`；小程序可沿用微信绿 `#07C160`，单端只保留一种主色 |
| 成功 | `#16803C` + 明确文字 |
| 警告 | `#B54708` + 明确文字 |
| 危险 | `#C4320A` + 明确文字 |
| 圆角 | 输入框/按钮 8px，卡片 10—12px |
| 阴影 | 默认不用；仅浮层或固定区使用极轻阴影 |
| 动效 | 只用短暂状态反馈；不使用装饰性入场、轮播或炫技动画 |

字体使用系统默认无衬线字体。员工小程序正文不小于 16px，辅助文字不小于 14px；管理员网页正文通常 14—16px。核心数量、任务状态和页面标题应形成清楚层级，不使用大段浅灰小字。

间距以 4px 为基础单位，常用 8/12/16/24/32px。相关字段靠近，不相关区块用留白分组，不依赖大量分割线。

## 3. 通用交互

- 可点击区域至少 44×44px，小程序主按钮建议高度 48px 以上。
- 按钮直接描述结果：“确认报货”“保存分货”“关闭批次”，避免只有“确定”。
- 一页只有一个明显主操作；次要操作降级为普通按钮或文字按钮，危险操作与主操作分开。
- 所有写操作必须有明确触发，不使用失焦即保存、左滑、长按或隐藏菜单。
- 提交期间禁用重复点击并显示“提交中”；成功与失败都用文字反馈。
- 保存失败必须保留输入。校验错误显示在字段附近，并在页面顶部提供汇总提示（若错误跨多个区域）。
- 二次确认只用于删除、关闭、重开、解锁等高风险动作；确认框要写明对象和影响。
- 状态使用“文字 + 颜色/形状”，不能只靠颜色。用词固定为：未分货、待报货、已报货、已锁定、已完成、已关闭。
- 数量输入使用合适数字键盘，允许一位小数；界面显示整数时不强制补 `.0`。

## 4. 员工微信小程序

### 4.1 信息架构

保持三层以内：

1. 手机号快捷登录（仅未登录时）。
2. 我的批次：首页默认突出待办，历史作为次级入口或下方区域。
3. 批次产品：只显示分给本人的产品卡片，卡片内完成报货。

不设置复杂底部导航；若只需要“待办”和“历史”，优先在一个页面用清晰分区或简单双标签完成。

### 4.2 批次与产品卡片

- 批次卡片首行显示批次名称，随后显示到货日期和“待报 N 项/已完成”。整张卡片可点击，同时保留明确的“去报货”文字。
- 产品卡片按“产品名称 → 分货数量 → 报货输入/已报结果 → 主按钮”从上到下排列。
- 分货数量必须在输入前清楚可见，例如“分给您：10.5 箱”。
- 待报时只展示一个大号输入框和“确认报货”；已锁定时移除输入框，显示“已报货 0/8.5”和“已锁定”。
- 报 0 合法。可在输入框下用短句解释：“没有货请填 0 后确认”。
- 超过分货量时就地提示“报货数量不能大于分货数量”，按钮保持不可提交。
- 不展示其他员工姓名、数量或公司级汇总。

### 4.3 历史加载

- 初次查询最近 90 天，待办始终优先于已完成历史。
- 上拉到底显示“正在加载更早记录”，每次增加 15 天；结束时显示“没有更早记录了”。
- 加载失败提供明显“重新加载”，不要清空已加载内容或重复卡片。

## 5. `frontend` 管理员网页

### 5.1 桌面布局

- 常用宽度从 1024px 起保证主流程可用。导航保持稳定，内容区最大化服务于批次矩阵。
- 首页只展示待处理批次、完成进度和“新建批次/继续分货”，不堆叠无行动价值的图表。
- 表单使用清晰标签和辅助说明；同一任务内字段排列符合操作顺序。

### 5.2 Excel 导入

- 使用四步但不做复杂向导：选择文件 → 查看全部校验结果 → 确认批次名称/日期与预览 → 创建批次。
- 错误表至少包含工作表、单元格、原值、原因，一次完整展示；支持定位/筛选，但不能只弹出第一条。
- 预览明确说明“导入产品不会匹配产品资料库”“员工将取系统全部启用员工”。
- 校验或创建失败不得留下看似已创建的批次，也不要丢失管理员已填的正式名称和日期。

### 5.3 分货矩阵

- 左侧固定产品名称、公司到货、总分货、总报货、剩余；顶部固定员工及分货/报货子列。
- 分货单元格可编辑，报货单元格始终只读。用视觉样式明显区分编辑与只读，但仍保留列标题文字。
- 当前产品的总分货和剩余在输入时即时更新；超量行标红并给出文字原因，保存按钮不可用。
- 显示未保存状态和保存结果。保存失败保留所有编辑值。
- 支持按产品简称搜索和按超量/待报/完成筛选；不要把高级筛选作为首屏必需操作。
- 数据很多时允许横向/纵向滚动，不设置固定产品或员工上限，也不把文字缩到难以阅读。

### 5.4 管理网页的移动浏览器适配

- 侧栏折叠，表单单列，主操作保持可见。
- 查看矩阵时可横向滚动；编辑时优先切换为“选择产品 → 员工分货列表”的卡片/抽屉，不在窄屏缩放整表。
- 至少保证登录、查看批次、编辑必要分货、保存、查看进度和执行解锁可完成。

## 6. `uniapp` 遗留管理员界面

- `uniapp` 中已有管理员页面、登录跳转、API 封装及打印/导出代码只做历史保留，不删除、不继续设计或扩展。
- 这些页面不作为正式入口，也不参与功能、视觉、真机或上线验收。
- 除非遗留代码阻塞员工端构建或运行，否则不要顺带整理；确实阻塞时只做解除阻塞所需的最小修改。
- 管理员手机操作统一由第 5.4 节所述的 `frontend` 移动浏览器布局承担。

## 7. 页面状态清单

任何新增页面或主要组件至少判断以下相关状态：

- 首次加载与局部提交中。
- 无批次、无待办、无搜索结果、无历史记录。
- 网络失败、会话过期、无权限、数据已被其他操作更新。
- 表单非法、分货超量、报货超量、超过一位小数。
- 可编辑、已提交锁定、管理员已解锁、批次已关闭。
- 操作成功，以及成功后页面应更新的状态和数量。

空状态直接告诉用户下一步，例如“暂无待报货任务”；错误状态给出可执行动作，例如“网络异常，请重新加载”。不要展示后端堆栈、原始 JSON 或内部错误码。

## 8. 可访问性与易用性检查

- 文本与背景对比清楚；占位符不能代替字段标签。
- 输入框获得焦点后页面不跳动、不遮挡当前字段和提交按钮。
- 键盘可操作管理员网页的表单、弹窗和矩阵常用输入；焦点顺序符合视觉顺序。
- 图标旁有文字或可访问名称；状态、错误和必填不只靠颜色。
- 文案使用普通工作语言，避免“实例化、同步、映射”等技术词直接面向员工。
- 不要求用户记住上一页数据；确认框和错误信息要带上批次、产品或员工名称。

## 9. 交付前检查清单

- 主任务能否用最短路径完成，是否出现额外登录、隐藏入口或不必要字段？
- 管理员是否只能填分货，员工是否只能填本人报货？
- 报 0、超量、一位小数、保存失败、重复点击和锁定状态是否正确呈现？
- 小程序是否只显示本人已分配产品，字体和触控区域是否足够？
- `frontend` 是否只继续开发管理员网页，已有员工网页代码是否保持未扩展且不作为正式入口？
- 管理网页的大矩阵是否保留上下文，移动浏览器适配是否可完成关键操作？
- `uniapp` 遗留管理员代码是否保持冻结，未被扩展或重新设为正式入口？
- 加载、空白、错误、成功、只读和无权限状态是否都有明确文字？
- 是否使用了统一颜色、间距、按钮层级和状态词，而没有新增装饰性复杂度？
- 是否完成目标端构建，并记录未完成的微信开发者工具或真机验证？
