# 分单系统开发准备与 AI 工作流

> 状态：开发前基线 1.0  
> 适用范围：后端、管理员响应式网页、员工微信小程序、数据迁移与部署

## 1. 开发是否可以开始

`需求分析.md` 已覆盖 MVP 的角色、主流程、数据口径、状态、权限、Excel 格式、界面原则和验收场景，业务需求已经达到开发就绪状态。后续若出现新想法，先判断是缺陷修复、实现细节还是需求变更；只有需求变更需要先修改需求文档并重新确认。

现有代码不能直接上线。首要风险是身份与权限、硬编码配置、员工端交互以及旧数据结构与新规则不一致。因此不能从“改页面样式”开始，应先建立可信的数据和认证底座。当前数据均为测试数据，可以按需删除并重建数据库，不需要保留旧结构或编写历史数据迁移。

## 2. AI 开发的标准循环

每个功能切片都按以下顺序执行：

1. **定位需求**：引用 `需求分析.md` 的具体章节和验收场景，写清本次不做什么。
2. **影响分析**：检查数据库、API、管理员网页、小程序、历史数据和配置是否受影响。
3. **设计最小方案**：列出数据结构、接口契约、页面状态、失败路径和迁移方式；复杂改动先形成可检查的计划。
4. **实现纵向切片**：后端权限与校验先于界面展示；管理员功能只在 `frontend` 响应式 Web 完成，员工功能只在 `uniapp` 完成，不留下只能演示成功路径的半成品。`uniapp` 已有管理员代码保留但冻结。
5. **分层验证**：依次验证单元/接口、构建、关键交互、权限越界和历史数据兼容。
6. **自我审查**：对照需求、`AGENTS.md` 和 UI skill 检查遗漏、重复规则、敏感配置及未经授权的范围扩大。
7. **交付记录**：说明改了什么、如何验证、需要什么配置或迁移、尚有哪些风险。

一次切片应尽量小到可以独立验收，例如“员工手机号登录闭环”或“Excel 解析与错误汇总”，不要一次把全部系统推倒重写。

## 3. 实施阶段与准入条件

### 阶段 0：基线与安全底座（P0）

- 梳理现有数据库并设计最终结构；直接重建测试数据库，不保留旧数据或编写历史迁移。
- 环境化 Flask 密钥、数据库地址、微信 AppID/Secret、API 基地址和运行模式。
- 建立统一认证、管理员角色校验、员工会话和标准错误响应。
- 删除对客户端 `user_id` 的身份信任，关闭生产调试模式和默认管理员凭据。
- 建立自动化测试入口和前后端可重复构建命令。

准入下一阶段：未登录、越权和伪造员工身份均被后端拒绝；开发环境可通过示例配置启动；测试数据库可通过明确命令安全重建。

### 阶段 1：基础资料与微信登录

- 员工姓名、唯一手机号、启停状态和内部 ID。
- 产品资料库与单位仅服务于手动建批，保留历史名称快照。
- 微信手机号凭证由后端换取手机号，匹配员工后建立会话；授权拒绝和未匹配均有清晰提示。
- 管理员账号只在 `frontend` 响应式网页使用；基础资料维护需同时覆盖桌面和移动浏览器。

准入下一阶段：需求验收场景 1、2 通过，停用资料不破坏历史展示。

### 阶段 2：Excel 导入与批次创建

- 严格按已审核模板解析，收集并一次返回全部单元格错误。
- 导入产品不匹配资料库；解析、校验和创建采用原子事务。
- 上传后确认正式批次名称和到货日期；手动建批从资料库选择产品。
- 创建批次时固化产品名称/单位快照和全部启用员工范围。
- `frontend` 管理端提供导入和手动建批能力，并在移动浏览器保留可用的文件选择、预览和错误展示流程。

准入下一阶段：需求验收场景 3—7 通过；失败导入不留下半成品数据。

### 阶段 3：管理员分货矩阵

- `frontend` 完成动态产品×员工矩阵、单元格编辑、三级汇总、搜索/筛选和移动浏览器适配。
- `frontend` 在移动浏览器使用卡片、分步编辑或可控横向滚动等方式完成同一管理员业务流程，不简单缩小桌面宽表。
- 后端强制校验最多一位小数、分货大于 0、总分货不超到货量。
- 大矩阵验证滚动、固定上下文和输入保留，不能只按参考截图的数据量测试。

准入下一阶段：需求验收场景 8—10 和汇总计算在 `frontend` 桌面与移动浏览器中通过，超量在界面提示且后端拒绝；刷新后状态和结果一致。

### 阶段 4：员工报货与管理员状态闭环

- `uniapp` 员工端只展示本人已分配任务；默认突出待办。
- 明确点击提交，支持报 0，成功后锁定；失败保留输入。
- `frontend` 管理员端能在桌面和移动浏览器执行解锁、关闭与重开；员工重报和批次自动完成形成完整状态机。
- 历史记录先取 15 天，上拉每次向前取 15 天，去重且显示结束状态。

准入下一阶段：需求验收场景 11—21 通过，重复提交不会产生重复记录或错误状态。

### 阶段 5：导出、端侧一致性与上线准备

- 页面、打印和 Excel 导出的字段与计算口径一致。
- 完成 `frontend` 管理员网页桌面/移动浏览器检查，以及 `uniapp` 员工端的常见屏幕真机检查。
- 对照管理员功能清单逐项验证 `frontend` 的桌面与移动浏览器流程，功能、权限、校验、状态和结果不得因屏幕尺寸缺项或冲突。
- 配置 HTTPS 合法域名、备份、日志、健康检查和生产部署说明。
- 使用脱敏数据执行完整回归，再执行上线前安全审查。

完成标准：22 个 MVP 验收场景全部有证据，P0/P1 差距清零，未解决事项被明确记录而非隐藏。

## 4. 接口与数据设计约束

- 金额式浮点误差同样会影响数量；服务端和数据库应使用固定精度数值，API 可接受数字或规范字符串，但返回格式必须统一。
- 创建批次、保存分货、提交报货、解锁、关闭和重开都必须在事务中完成。
- 员工重复点击同一提交请求时应返回当前成功结果，不得创建重复报货记录；客户端按钮同时防重复点击。
- 导入先解析到临时结构，全部校验通过后再一次性写库。
- 当前值与历史事实分开：批次保存姓名/产品名/单位快照；报货解锁不抹除原值；关键管理操作保留审计记录。
- 时间由服务端生成并统一保存，界面按 `Asia/Shanghai` 展示；分页使用稳定排序键，避免历史加载重复或遗漏。

## 5. 验证矩阵

| 变更类型 | 最低验证要求 |
| --- | --- |
| 后端业务规则 | 自动化测试 + 未登录/越权/边界值接口测试 |
| 数据模型或重建 | 空库创建 + 测试库清空重建 + 种子数据显式配置；本阶段不验证历史迁移 |
| 管理员网页 | `npm run build` + 桌面主流程 + 移动浏览器关键流程；不扩展现有员工网页界面 |
| `uniapp` 员工端 | `npm run build:mp-weixin` + 微信开发者工具/真机报货与历史流程 |
| Excel 导入导出 | 合法模板 + 多错误模板 + 大数据量 + 数值格式复核 |
| 状态与锁定 | 正常提交、报 0、重复提交、解锁重报、关闭重开、并发冲突 |
| UI 改动 | `.codex/skills/xitong-ui/references/ui-spec.md` 全部相关项 |

## 6. 每次任务的建议提示模板

```text
请先阅读 AGENTS.md、需求分析.md 中与本任务相关的章节，以及必要的项目 skill。
本次只完成：[一个可验收的纵向功能切片]。
开始修改前先报告需求依据、影响范围、数据迁移风险和验证计划；然后完成实现与验证。
不要扩大范围，不要改写已确认的业务规则，不要把未运行的测试说成已通过。
```

## 7. 首个代码任务建议

第一项代码工作是“阶段 0：认证、配置与测试数据库重建设计”，而不是先重做界面。先生成当前数据库结构、API 和敏感配置清单，然后直接建立可重复清空重建的最终测试结构；无需等待历史迁移确认。
